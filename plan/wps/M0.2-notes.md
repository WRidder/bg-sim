## Orchestrator notes

### 1. You must also lay down the minimal test harnesses (M0.4 and M0.5 extend them)
Your acceptance requires a pytest and a vitest, but `backend/` and `web/` do not exist yet. Create
the minimum needed, and say so in your report so the later WPs extend rather than replace:

- `backend/`: `uv init --package bgsim-server` inside `backend/`, then `uv python pin 3.13`,
  then `uv add --dev pytest pytest-asyncio httpx ruff datamodel-code-generator` and
  `uv add jsonschema`. Add `backend/src/bgsim_server/__init__.py` and
  `backend/tests/test_contracts.py`. Keep it to contracts concerns only: no FastAPI yet
  (M0.4 owns that).
- `web/`: a minimal `package.json` (name `bgsim-web`, `"type": "module"`) with devDependencies
  `vitest`, `ajv`, `ajv-formats`, `typescript`, `json-schema-to-typescript`, and npm scripts
  `test` (vitest run), `typecheck` (tsc --noEmit). Plus `tsconfig.json`, `vitest.config.ts`
  and `web/tests/contracts.test.ts`. **Do not add React, Vite or anything from plan 7.1** —
  M0.5 owns the real web app and will add those.

### 2. Fixture layout (self-describing, so both test suites can walk it)
```
contracts/
  schemas/<name>.schema.json            # JSON Schema 2020-12
  fixtures/<name>/valid/*.json          # every file must validate
  fixtures/<name>/invalid/*.json        # every file must FAIL to validate
  fixtures/run-manifest/valid/run.synthetic/{manifest.json,generate.py}
  README.md                             # the conventions you chose, in 10 lines
```
`<name>` is the schema base name: `catalog`, `model`, `project`, `diagnostic`,
`run-manifest`, `worker-rpc`, `stream-handshake`, `bindings`.
Every schema gets `"$id": "https://bgsim.local/schemas/<name>.schema.json"` and cross-schema
references use that absolute `$id` (register every schema in both toolchains before
validating). Keep the section 3 fixture file names (`catalog.min.json`,
`model.dcmotor.json`, `diagnostics.sample.json`, `run.synthetic/`).

### 3. Coverage requirements
- `diagnostics.sample.json` (in `fixtures/diagnostic/valid/`) must contain **one instance of
  every code in the spec table plus D14's additions**: E000, E001, E002, E003, E004, E005,
  E006, E101, E102, E103, E104, E105, E106, E900, E901, W201, W202, W203, W204, W205, W206,
  and the viewer codes E301, E302, E303, E304. Make the messages and hints realistic, and give
  each one a path, and node/connection/source where the shape allows it.
- `catalog.min.json` must cover the M1 blocks of plan section 8: Se, Sf, MSe, C, I, R, TF, GY,
  De, Df, junctions 0 and 1, Constant, Step, Sine, Gain, Sum, Integrator, PIController,
  Resistor, Capacitor, Inductor, Ground, VoltageSource, Mass, Spring, Damper, Fixed,
  ForceSource, Inertia, TorsionSpring, RotationalDamper, FixedShaft, TorqueSource, IdealGear,
  DCMotor, SpeedSensor, AngleSensor — with realistic `constants`/`parameters`/`inputs`/
  `outputs`/`ports`/`variables`/`causality` and the real `@block` source text in `source`.
  Use the spec's parameter names (`C` has `c` with `unit = "flow*s/effort"`, `GearBacklash` is
  not needed yet). Include the `junctions` and `domains` arrays with Electrical, Translation,
  Rotation, Hydraulic and Generic per plan 3.2.
- `model.dcmotor.json` is the plan 9.1 **iconic** DC-motor model: a VoltageSource (Step),
  DCMotor, Ground, two Fixed shafts, a Rotational damper, connected with `bond` and `wire`
  connections, plus one signal connection. It must carry `settings`, `plots`, `scene: null`
  and `bindings: []`.
- `worker-rpc`: request, response, error and notification fixtures, and one invalid
  (unknown method / missing id).
- `stream-handshake`: the ordered signal list + rate.
- `bindings`: the four spec examples (joint position, link pose with 7 signals, visual scale,
  visual colour with colormap and range) plus a Bool `visible`.
- Invalid fixtures: at least two per schema, each invalid for a *different* reason, and the
  reason written in a top-level `"$comment"` field (which the schemas must not forbid, i.e.
  allow `$comment` or make the invalid fixture invalid in a way that is not about `$comment`).
  Simplest: give every schema `"$comment": {}`-friendly handling by adding `"$comment"` to the
  allowed properties where needed. Prefer making invalid fixtures invalid by *omitting a
  required field* or by a *wrong type/enum*, so `additionalProperties: false` still holds.

### 4. Generated code
- Python: `datamodel-code-generator` → `backend/src/bgsim_server/contracts.py`
  (`--output-model-type pydantic_v2.BaseModel --input-file-type jsonschema
  --target-python-version 3.13`). It must import cleanly and every schema must produce a model.
  If the generator chokes on JSON Schema 2020-12 keywords, reduce those keywords in the
  schema (keep the contract honest) rather than hand-editing the output. Verify:
  `uv run --directory backend python -c "from bgsim_server.contracts import Model; print(Model)"`.
- TypeScript: `json-schema-to-typescript` → `web/src/contracts/*.ts` plus an `index.ts`.
  Must pass `npm run typecheck` in `web/`.
- `tools/gen_contracts.py` is a uv script (`# /// script` header) that regenerates both from
  `contracts/schemas/` deterministically and prints a summary. Run it from the repo root as
  `uv run tools/gen_contracts.py`. It must be re-runnable with no diff on a clean tree.
- Commit nothing yourself; the orchestrator commits.

### 5. Run fixture generator
`contracts/fixtures/run-manifest/valid/run.synthetic/generate.py` is a uv script with inline
dependencies (`numpy`) that writes `columns.f64` and `stream.f64` next to itself (or into an
argv directory). `*.f64` is gitignored, so the pytest test must generate the files if they are
missing, then assert: file size == n_signals * n * 8 bytes, little-endian Float64, the time
column is monotone, and a known sine/step value at a known index matches `numpy.sin`. The
manifest must list exactly those signals in that order, with `layout: "columnar-f64-v1"`.
