## Orchestrator notes

### 1. What is done when you start
J1.6 lands just before you: the real worker serves `catalog.get`, `block.check`, `model.check`,
`run.start`/`run.cancel` and the `run.*` notifications, and the backend's `@pytest.mark.julia`
tests pass. P1.1/P1.2/P1.3 and W1.1–W1.4 are done, so the editor, run bar and plots work.
`uv run bgsim` starts the backend (real worker unless `BGSIM_FAKE_WORKER=1`), on
`127.0.0.1:8765`, and serves `web/dist`.

### 2. The example (plan 9.1)
Copy and adapt `contracts/fixtures/model/valid/model.dcmotor.json` (iconic, 7 connections after
CONTRACT-3) and `model.dcmotor.bondgraph.json` into `examples/dc-motor/models/`. Keep the
parameters exactly: `R = 2`, `L = 5e-4`, `k_t = 0.05`, `J = 1e-5`, `d = 1e-6` (realised as the
separate `RotationalDamper` with `d = 1e-6`, and `DCMotor.d = 0`), a 12 V step at
`t = 0.01 s`, `t_end = 1.0 s`.
Two important facts the Julia lane established, so do not "fix" them:
- the iconic model's steady state is `ω = k·V/(k² + R·d) = 239.80815347721824 rad/s`;
- the bond-graph fixture uses a constant 12 V `Se` (no step), so transient comparison starts at
  `t = 0.5 s`; the settled values agree to 5.7e-14.
Files:

Validate both model documents against `model.schema.json` (the backend's `PUT` does it; a test

### 3. `expected.json` and `examples/run_checks.py`
`expected.json` is machine-readable and you document its meaning in the README. Suggested shape:
```json
{ "project": "dc-motor",
  "models": {
    "iconic": { "checks": [
        { "kind": "final_value", "signal": "Motor1/shaft.f", "t": 1.0, "value": 239.80815347721824, "rtol": 1e-4 },
        { "kind": "cursor_value", "signal": "Motor1/shaft.f", "t": 0.2, "value": 239.8, "abs": 0.1 } ] },
    "bondgraph": { "checks": [
        { "kind": "final_value", "signal": "IJ/p.f", "t": 1.0, "value": 239.80815347721824, "rtol": 1e-4 } ] },
    "compare": { "a": "iconic", "b": "bondgraph", "signal_a": "Motor1/shaft.f", "signal_b": "IJ/p.f",
                 "from_t": 0.5, "max_abs": 1e-6 } } }
```
`examples/run_checks.py` is a **uv script** (inline dependencies: numpy; `httpx` for the HTTP
calls) that discovers every `examples/<name>/expected.json`, starts the backend once (spawn
`uv run bgsim` with the real worker on a free port via `BGSIM_PORT_HTTP`, wait for
`worker: "ready"`), then for each check: creates/opens the project through the API, runs the
model, reads `<project>/runs/<id>/columns.f64` with `numpy.memmap` using the manifest's
`signals` order, and evaluates the check. Print one line per check and exit non-zero on any
failure. Stop the backend in a `finally`. Target: the whole suite under ~90 s warm.
The `cursor_value` check at `t = 0.2 s` is the number the Playwright test asserts; keep them
identical (239.8 ± 0.1).

### 4. Playwright
`web/tests/e2e/dcmotor.spec.ts` against the **real** worker (`BGSIM_E2E_REAL=1`, which
`web/playwright.config.ts` already honours by not forcing the fake): open the DC motor example
(project list → open, or a direct `/?project=dc-motor&model=iconic` URL if the UI supports it —
read `web/src/state/session.ts`), press Run, add `Motor1/shaft.f` to a plot, and assert the
legend/cursor readout at `t = 0.2 s` shows `239.8` within 0.1. Use the existing test ids
(`run-button`, `signal-item`, `plot-chart`, `legend-item`, `legend-time`). If the example
project does not appear in the start page yet (W3.4 adds the gallery), open it through the API
(`POST /api/projects {"name": "dc-motor", "example": "dc-motor"}`) in the test's setup, then
navigate. Keep the test under 90 s including the worker start.
