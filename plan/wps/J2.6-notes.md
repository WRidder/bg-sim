## Orchestrator notes

### 1. What to read
The spec's worked example `GearWithBacklash` (spec section "Worked example: gear with backlash
and efficiency") is normative and is your acceptance target. Plan D5 says `@components` /
`@connections` are the **textual form of a subsystem**, so a block written that way must
flatten exactly like the equivalent model-JSON subsystem. J1.1 rejected those scopes with a
named E001; you remove that rejection (in `src/syntax/scopes.jl`) and implement them.

### 2. Syntax to support
```julia
@block GearWithBacklash begin
    @ports begin
        a::Power{Rotation}
        b::Power{Rotation}
    end
    @components begin
        gear = LossyGear(n = 10.0, eta = 0.9)
        play = GearBacklash(k = 1e4, d = 5.0, gap = 0.01)
    end
    @connections begin
        connect(a, gear.a)
        connect(gear.b, play.a)
        connect(play.b, b)
    end
end
```
- `@components`: `name = BlockRef(args...)`, keyword arguments are parameter expressions
  (the same expression scopes as defaults), positional arguments are not needed.
- `@connections`: `connect(portA, portB)` where each side is either a port of this block or
  `instance.port`. Both kinds (signal and power) must work. Refuse: connecting two siblings
  that are both not ports of this block? No — `connect(gear.b, play.a)` is exactly that, so
  instance-to-instance is allowed. Refuse instead: a component name that collides with a port
  or a declaration; a referenced component or port that does not exist (E003); connecting a
  port to itself; connecting two ports of different kinds/domains (E102 at instantiation).
- The interface of the composite block is its `@ports`/`@inputs`/`@outputs`; `@components`
  blocks are flattened away with the `<instance>/` name prefix inside the composite's own path
  (e.g. `Gear1/gear/n`).

### 3. Instantiation
`src/compile/instantiate.jl` already expands model-JSON subsystems recursively with path
prefixes (J1.4). Reuse that machinery: a composite `BlockDef` with components becomes a nested
instantiation with the same prefix rule, and its `@connections` become the same connection
equations the model-JSON flattener generates. The cleanest implementation is to lower the
textual composite into the same intermediate representation a JSON subsystem produces, so there
is exactly one code path. **The acceptance test depends on this**: the same structure built
from text and from JSON must be bit-identical on the same solver.

### 4. DCMotor as a composite
Rewrite `stdlib/converters/DCMotor.jl` as a composite with
`@components` of `MTF`/`GY`/`R`/`I`-like parts (the classic electrical→mechanical gyrator
chain: winding R and L on the electrical side, GY(k_t), rotor I(J) and R(d) on the shaft side,
with `shaft`/`housing` as the composite's rotation ports). Keep the **interface identical**:
ports `p, n, shaft, housing`, parameters `R, L, k_t, J, d` with the same units and defaults, so
every existing model and test still works. If the composite form cannot reproduce the flat
behaviour exactly (it should, since the flat form is the same equations), keep the flat block
and say so — but then `GearWithBacklash` is still yours and the textual composite must work.

### 5. Tests
- the spec's `GearWithBacklash` parses with zero diagnostics, its interface is `a`/`b` with
  `Power{Rotation}`, and it **simulates**: drive `a` with a rotary source / inertia, connect `b`
  to an inertia, and assert the backlash dead zone transmits no torque inside the gap and the
  full stiffness outside it (a small script with two operating points is enough).
- the text-vs-JSON equivalence: build `GearWithBacklash` from the text composite and the same
  structure as a model JSON with a subsystem node, flatten both, and assert the equation
  multisets are equal (as symbolic expressions) and that the simulated output columns are
  bit-identical on the same solver and settings.
- `DCMotor` composite (if you convert it): the DC motor golden checks from plan 9.1 must still
  pass, unchanged.
