### 2. `julia/BGSim/NOTES.md` is authoritative for the MTK API
Read it in full before writing code. The critical facts:
- `System(eqs, t, vars, pars; name, continuous_events, initialization_eqs)` → `mtkcompile`
  → `ODEProblem(sys, op, tspan)` with **one merged operating-point map**;
- `getu(integ, sym)(integ)` for observed values; `setp(integ, sym)(integ, v)` for parameters;
  `integ.u` for the whole state vector; `getu`, `setp`, `getp`, `setu` are not exported;
- never parse MTK-generated names: keep a `Dict{String,Num}` from signal ID to variable, as
  plan 5.8 requires;
- `ifelse` does **not** create callbacks; MTK adds none. Events are J2.3, but you must leave
  the seam: collect nonsmooth conditions in a function `nonsmooth_conditions(flat)` returning
  an empty vector for now, and pass `continuous_events = SymbolicContinuousCallback.(...)` to
  `System` so J2.3 only fills the collector.
- `Pre(...)` is required in affect equations; the `Pair` form auto-wraps.

### 3. What to build (plan 5.8 without events/discrete, and 5.10)
- `src/lower/fnmap.jl`: the whitelist function → Symbolics mapping (sin, cos, …, `abs`, `min`,
  `max`, `clamp`, `hypot`, `dot`, `norm`, `cross`, `transpose`, `A*x`, `A\b`, `floor`, `ceil`,
  `round`, `mod`, `rem`, `sqrt`, `exp`, `log`, `log10`, `sign`, `tanh`, …). `ddt` → `D`
  (`ModelingToolkit.D_nounits`), `int(x, x0)` → a new state with `D(x) ~ ...` and an initial
  equation. `ifelse` → `ifelse`. Nonsmooth functions that Symbolics cannot handle are
  rewritten into `ifelse` forms (e.g. `clamp(x, lo, hi)` → `ifelse`).
- `src/lower/mtk.jl`: build the `System`, `mtkcompile` it, build the `ODEProblem`; solver
  selection per plan 5.8 (`"auto"` → `Rodas5P()` when the system has a mass matrix or
  algebraic equations, else `Tsit5()`; the user may pick `FBDF`, `Rodas5P`, `Tsit5`, `Vern7`).
  Use the split OrdinaryDiffEq sub-packages that are already dependencies.
- `src/sim/simulate.jl`: the run loop. Settings from the model document (plan 3.3):
  `t_start, t_end, solver, reltol, abstol, max_step, output.mode` (`points` or `interval`),
  `event_limit`. Cancellation through an atomic flag checked every integrator step. Progress
  notifications through a callback. Solver failure → **E901** with `t` and the five states of
  largest magnitude (plan 5.11). `ExtraEquationsSystemException`/`ExtraVariablesSystemException`
  → E103; singular initialization → E103 with "initial conditions inconsistent"; anything else
  → E900 with the exception text in `hint` and the last-touched block path.
- `src/sim/recorder.jl`: one `getu` getter for all recorded symbols; append rows to
  `stream.f64` buffered and flushed at least every 100 ms; at the end write `columns.f64` and
  `manifest.json`. Layout exactly as plan 3.5 (`columnar-f64-v1`, row-major `[t, v1 … vn]`
  little-endian Float64 rows for the stream; time column then one column per signal in
  manifest order for the columns file; Bool/Int stored as Float64; event instants recorded
  twice as left and right limits — the event part is J2.3, but the writer must support
  duplicate `t` rows from the start). A test must round-trip `columns.f64` through
  `numpy.memmap` semantics: read it in Julia, assert the size, the time column and that a
  known analytic value matches.
- Compile cache (plan 5.8, D4): key on the structural hash (block sources, constants,
  topology, settings that affect structure); parameter values and start values are **not** in
  the key. On a hit reuse the compiled system and the problem through `remake(prob; u0, p)`.
  J2.8 does the full cache WP, but you must build the hash and the `remake` path now, because
  your acceptance includes "a parameter-only re-run hits the cache".

### 4. The DC motor checks (plan 9.1) inside the Julia tests
Build the two model fixtures with the J1.4 flattener, lower, simulate, and assert:
- steady state `ω = k·V/(R·d + k²) = 239.81 rad/s` (rtol 1e-4);
- iconic and bond graph agree (max abs difference < 1e-6 rad/s);
with `R = 2 Ω, L = 0.5 mH, k = 0.05 N·m/A, J = 1e-5 kg·m², d = 1e-6 N·m·s/rad`, a 12 V step
at `t = 0.01 s` and the damping `d` in a separate rotational damper between `shaft` and a
second Fixed shaft (plan 9.1). Keep them as Julia tests; `X1.1` re-runs them through the API.
Record the measured first-run and parameter-only re-run times in your report (plan 5.12:
first run < 10 s, parameter-only < 300 ms warm). The warm-up fact from NOTES.md applies: the
first `remake`+`solve` after a parameter change pays JIT, so measure the *second* one and say
so.
