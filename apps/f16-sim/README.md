# f16-sim: fly the bg-sim F-16 FMU

A small, standalone real-time flight simulator around the FMU that bg-sim exports from the
`f16-sim` model of the F-16 example (`examples/f16/models/f16-sim`: the Stevens & Lewis nonlinear
F-16 with a three-axis fly-by-wire). The FMU is the flight model; this app adds the pilot's inputs,
the world, the cameras and the HUD. Start airborne or on the runway, fly, land or crash, press R.

The airspace also holds up to three target drones. A second FMU, the AIM-9X of
`examples/aim9x/models/aim9x-fmu` (the weapon model with the host target interface), is loaded once
per wingtip shot; it guides to the target you have locked. The drones, the seeker cue and the lock
are in the host, the missile's flight and guidance are in the FMU.

Everything you see is generated here or comes from the examples: the aircraft and target meshes are
the examples' own (`examples/f16/meshes`, `examples/aim9x/meshes`), the terrain, airfield, town,
masts, wind turbines, clouds and rings are procedural.

## Why here, and why these libraries

* **`apps/f16-sim`**, not under `examples/`: creating a project from an example copies the whole
  example folder, and this app has its own virtual environment and build output. It is not part
  of the backend or the web app either: it only consumes the exported FMU. Its own
  `pyproject.toml` and `uv.lock` keep its dependencies (Panda3D, pygame-ce, fmpy) out of the
  bg-sim workspace.
* **fmpy** loads and steps the FMU (FMI 2.0 co-simulation) through ctypes.
* **Panda3D** (+ `panda3d-gltf`) renders: pip wheels for Windows, Linux and macOS (no engine to
  install), a glTF loader for the example's GLB meshes, offscreen buffers for headless runs and
  fixed-step video capture, and a 2D layer for the HUD, all driven from Python with one call per
  frame. A game engine with an editor (Godot, Unity) would need a second language and a plugin
  for the FMU; pygame/OpenGL by hand would need a loader, a scene graph and text rendering.
* **pygame-ce** (SDL2) reads joysticks, pedals and throttles. Only its joystick API is used: the
  window is Panda3D's, SDL runs with the dummy video driver and reads devices in the background.

## Install and build

Needs [uv](https://docs.astral.sh/uv/), Julia (`julia` on the PATH, as for bg-sim) and a C
compiler (gcc, as for the bg-sim FMU export).

    cd apps/f16-sim
    uv sync                      # the app's environment (Python 3.13)
    uv run build_fmu.py          # export + build both FMUs, write the start list

`build_fmu.py` runs `julia --project=julia/BGSim examples/export_f16.jl <tmp> --no-reference`
(the export of `f16-sim` with the host interface) and `examples/export_aim9x.jl` (the export of
`aim9x-fmu` with the target inputs and missile outputs), builds both with
`bgsim_server.fmu_build` (the hot-path checks: no allocation after instantiate, no forbidden
symbol, the doStep timing), and writes into `build/` (not committed):

| file | content |
| --- | --- |
| `build/f16_sim.fmu` | the F-16 FMU (about 120 KB) |
| `build/aim9x_fmu.fmu` | the AIM-9X FMU (about 110 KB), one instance per shot |
| `build/build.json`, `build/missiles.json` | method, internal step, doStep cost, compiler and the missile interface/ranges |
| `build/starts.json` | the start conditions: level-flight trims from `examples/f16/design/simscen.trim_globals`, checked against the FMU's parameter ranges |

Rebuild after changing a model. `uv run build_fmu.py --skip-export` rewrites only the starts;
`--skip-missile` builds only the F-16 FMU. The AIM-9X model is generated by
`examples/aim9x/design/build_fmu_model.py` from `aim9x-intercept`.

## Fly

    uv run f16sim                    # start condition 1; --start N picks another (0-based)
    uv run f16sim --rings            # with the ring course
    uv run f16sim --list-devices     # joysticks, pedals and throttles SDL sees
    uv run f16sim --missile-fmu build/aim9x_fmu.fmu   # another AIM-9X build
    uv run f16sim --no-missiles      # fly without the AIM-9X FMU (the drones still fly)

| key | action |
| --- | --- |
| arrows, or W/S and A/D | stick (spring back to the centre when released); down/S = pull |
| Q/E or Z/X | pedals (left/right) |
| PgUp/PgDn or +/- | throttle (0 idle, 77 % military, 100 % full afterburner) |
| U | gear handle (with weight on the wheels the gear stays down) |
| B | wheel brakes, held |
| C | chase view / cockpit (HUD) view |
| P | pause |
| R | reset to the current start condition |
| 1 .. 8 | reset to start condition N (the list is under F1) |
| G | ring course on/off (gates ahead of you; the next one pulses yellow, an amber circle on the HUD points to it) |
| T | turbulence on/off |
| M | fire the next AIM-9X (only with a seeker lock) |
| Tab or N | select the next target drone |
| L, V, Y | alpha/g limiter, velocity-vector roll, yaw damper on/off: FMU parameters, so the flight restarts |
| F1 | help |
| Esc | quit |

Start conditions (`build/starts.json`): cruise 500 ft/s at 10 000 ft, slow 300 ft/s at 10 000 ft,
700 ft/s at 5 000 ft, 900 ft/s at 2 000 ft, 600 ft/s at 20 000 ft, 350 ft/s at 2 000 ft, all trimmed
level, heading north, CG 0.35, gear up. Start 7 (`--start 6`) is on the south end of the runway at rest,
gear down, idle; start 8 (`--start 7`) is on a 3 deg final approach at 148 kt, 3 km out, gear down.

On the wheels the pedals steer the nose wheel (32 deg at taxi speed, falling with speed so that full pedal stays near 0.35 g).
Full aft stick lifts the nose at about 150 kt with full afterburner. The stick drives the stabilator
directly on the ground, and the fly-by-wire laws fade in as the weight leaves the main wheels.

## Drones, lock-on and the AIM-9X

Up to three target drones fly in the play area. They spawn ahead of the aircraft, fan out, fly
straight with a gentle turn, and are replaced four seconds after a hit. The HUD has a north-up
minimap at the lower left: the aircraft is the green triangle at the centre, every live drone is a
red diamond, the selected one has an amber ring and a locked one a green ring. The map covers 8 km;
contacts beyond it are clamped to the edge.

The seeker cue follows the real AIM-9X loop:

* the imaging infrared seeker has a **90 deg total field of view** (45 deg off boresight) and a 60 deg
  gimbal, and it needs an infrared source above its detection threshold;
* in the aircraft, the seeker is cued by the radar or the helmet-mounted cueing system, not by the
  pilot's eyeball; the pilot selects a target, points (or cues) the seeker within its field, and the
  seeker builds a track. When the track is steady the pilot hears the lock tone and gets the reticle
  (the real AIM-9X can also be fired with a lock after launch, using its datalink, in later blocks);
* this app selects the drone nearest the nose automatically, or the next one with `Tab`, and builds
  the lock over **one second** while the target is within 45 deg of the nose and within about 7 km
  (the IR threshold). Leaving the field breaks the lock. `M` fires only with a lock; the missile then
  has its own seeker and proportional navigation in the FMU.

The HUD shows `SEEKER` with the track percentage while it builds, `LOCK` with the range when it is
ready, and `M: FOX 2`; a selected target outside the cue reads `OUT OF FOV` or `TOO FAR`. The missile
is a fresh FMU instance per wingtip station (two per sortie), launched from the rail with the
aircraft's speed and heading. The fuze flash is the FMU's `fuze`/`hit` status; the target is removed
and a replacement drones in.

### Devices

`config/devices.toml` maps each control (pitch, roll, yaw, throttle) to one axis of one device,
matched by a part of the device name or by index, with inversion, dead zone, expo and the range
(`bipolar` for sticks and pedals, `unipolar` for a throttle). Rudder pedals are a separate device
(`[yaw] device = "pedal"` by default); a throttle quadrant too (`[throttle] device = "throttle"`).
A control without a matching device falls back to the keyboard. The keyboard also works next to a
bound device: per control, the input touched last wins (the keys take over while held, the device
takes back when its axis moves), so a device that SDL lists first but nobody flies with (a 3D mouse
driver's "KMJ Emulator", a gamepad) cannot lock out the arrow keys. The bindings are printed at
start. Use `--config other.toml` for another set, `--no-joystick` to ignore all devices. Run `--list-devices` and move each axis to find
its number.

## The HUD

Cockpit view (conformal: one degree on the HUD is one degree of the view): pitch ladder (solid
above, dashed below the horizon) rolled with the bank, waterline, flight-path marker (where the
aircraft goes: alpha below and beta beside the nose), heading tape, CAS (kt) and altitude (ft)
boxes, vertical speed, Mach, g, alpha, beta, throttle and engine power (AB above military), bank.
The chase view keeps the numbers, the tape and the warnings.

Warnings (blinking): `DEPARTED` (the model's departure flag: alpha beyond -15..35 deg or |beta| >
15 deg), `PULL UP` (below 600 m above the terrain and less than 8 s to impact), `STALL` (alpha above
22 deg or CAS below 130 kt), `G LIMIT` / `ALPHA/G LIMIT` (the limiter cuts the pilot's command:
the model's `limiter_active`). `CRASHED` freezes the flight (the FMU's ground contact, or the
terrain's hills, which the FMU does not know); R resets. The top line shows the frame rate, the
real-time factor, the sim time, the view, the start condition, frames whose backlog was dropped
and the law switches that are off.

## Architecture

    devices.toml -> inputs.py (SDL joysticks, keyboard) --+
    scripts.py (scripted inputs) -------------------------+--> core.Simulation --> fmu.FlightModel --> F-16 FMU (fmpy)
                                                                   |   pacer, crash, rings, wind        missile_model.MissileManager --> AIM-9X FMUs (fmpy)
                                                                   |   drones, seeker lock, missile shots
    game.py (Panda3D ShowBase, one thread) <-----------------------+
       world.py (terrain, airfield, landmarks, sky, clouds, rings), aircraft.py (meshes, surfaces),
       missile_view.py (missile and drone meshes, canards, plumes, flashes), hud.py (HUD, lock cue, minimap)

* **One thread, fixed steps.** Both FMU families run on the same 5 ms communication step. A missile
  costs about 15-30 us of doStep through fmpy, so two live shots add a small fraction of the F-16's
  cost. Each shot is a `FMU2Slave` instance from one extracted AIM-9X FMU; instances are never freed
  one by one (fmpy's `freeInstance` unloads the shared library), only all together on reset/close.
* **Missile coordinate frame.** The FMU flies in a launch frame (x north, y west, z up), with x/y
  relative to the launch point and z the absolute altitude. `missile_model` rotates the target into
  that frame and the pose back to world NED; `missile_view` uses the same world matrix as the F-16.
* **Drones and lock.** `tactical.py` is pure state (no Panda3D): the kinematic drones, the 8 km
  minimap contacts and the one-second seeker lock. `Simulation.step_once` advances the F-16, the
  drones, the lock and the missiles in that order, so the target data the FMU sees belongs to the
  step just run.
* **Bounded catch-up.** A frame later than 100 ms (a window drag, a slow machine) runs 20 steps
  and drops the rest of the backlog: the flight slows down instead of spiralling. The top line
  counts those frames (`behind`).
* **Interpolation.** The drawn position, attitude and surfaces are interpolated between the last
  two steps by the accumulator's fraction, so the picture moves evenly although the steps per
  frame alternate between 3 and 4 (the state shown lags the newest step by less than 5 ms).
* **Inputs** are held over each step (zero-order hold), as in the FMU's reference runs.
* **Coordinates.** The FMU gives NED position and the body-to-NED quaternion (body x forward, y
  right, z down). Panda3D's world is x east, y north, z up; the meshes are x forward, y left, z
  up. `aircraft.world_matrix` composes the three. The control surfaces turn about the hinge lines
  of the bg-sim scene (`examples/f16/scenes/f16-sim.sdf`).
* **Reset** re-instantiates the FMU: the trim (vt0, h0, alpha0, el0, thtl0), the CG and the law
  switches are FMU parameters that can only be set before initialisation.

## Tests

    uv run pytest                                     # core: pacer, input shaping, FMU in closed loop
    uv run pytest tests/test_missile.py               # drones, lock, one and two AIM-9X instances
    uv run f16sim --headless --seconds 10             # smoke: 10 s scripted, rendered offscreen
    uv run f16sim --headless --seconds 14 --script missile   # two launches, lock, hit
    uv run f16sim --quit-after 8                      # the real-time window for 8 s, with a summary

The FMU tests skip without `build/f16_sim.fmu`. They check that the trim holds level flight, that
right roll stick rolls and turns right with |beta| < 1 deg, that full aft stick sets the limiter
flag below 9.3 g and 26 deg alpha, that the quaternion matches the Euler angles and that a reset
restarts at the trim. On the gear they check that the aircraft rests on the runway with its weight on
the wheels, that the pedals steer it, that the approach start lands, and that the ground is still a
crash with the gear up. The missile tests skip without `build/aim9x_fmu.fmu`: they check the
one-second seeker cue and its 45 deg break, the three-drone cap and replacement, the launch-frame
target conversion, a shot that flies and fires the fuze, and two independent FMU instances flying
opposite headings.

## Video

    uv run f16sim --record out.mp4 --script demo --fps 60 --ffmpeg <path to ffmpeg>
    uv run f16sim --record out.mp4 --script missile --fps 60 --ffmpeg <path to ffmpeg>

renders the `demo` script (`scripts.py`: a full-stick roll, a coordinated 60 deg turn, a hard pull
into the limiter in an 80 deg bank, chase and cockpit views) offscreen at fixed 1/60 s frames, at
twice the size, and pipes the frames to ffmpeg (H.264, yuv420p, downscaled). The `missile` script
holds the target in the cue, fires both wingtip AIM-9Xs, and switches to the cockpit for the hit.
A folder instead of an `.mp4` writes PNG frames.

## Limitations

* The aerodynamics are the book's low-speed NASA TP-1538 data (no Mach effects): above about
  Mach 0.6 it flies like the model, not like an F-16. Beyond alpha 45 deg or beta 30 deg the tables
  hold their edge values, so post-departure motion is qualitative.
* The target drones are kinematic sources, not aircraft FMUs: they fly straight with a gentle turn
  and no AI. At most three are alive; the minimap is 8 km across and clamps contacts outside it.
* The host lock is an approximation of the real cue: the real seeker is slaved to the radar or the
  helmet-mounted cueing system and measures infrared contrast; here `Tab` selects a drone and the
  nose must be within 45 deg and about 7 km for one second. The FMU's own seeker, gimbal, IR
  threshold and proportional navigation then run the shot; flares and IRCCM are not modelled.
* The launch state taken from the F-16 is its speed, altitude and heading, not its bank or flight-path angle; a shot from a steep bank starts wings-level and the missile rolls/levels in the FMU.
* A sortie carries two wingtip missiles. The AIM-9X model carries no fuze stop in the host variant:
  the app latches `fuze`/`hit` and retires the instance. The target drone visual is a red F-16
  airframe, a stand-in for the target.
* The missiles are one FMU instance per shot, sharing an extracted library; they are freed together
  on reset/close (fmpy unloads the library with an instance). Resetting also resets the drones and
  the lock.
* The hills are the host's: the FMU's ground is flat at 0 m, so the wheels roll at height 0 and the
  runway must lie at 0 m. Off the airfield the host checks the terrain height itself. Wind and turbulence are a steady wind plus filtered
  noise, not a Dryden model.
* Changing the mass (an FMU parameter) without a new trim starts the flight out of trim.
* With vertical sync on, a window in the background may be throttled by the desktop compositor
  (seen here: 26 fps unfocused, 135 fps with `--vsync 0`); the pacer keeps the simulation in
  real time either way.
